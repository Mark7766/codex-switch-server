### 3.9 生产环境专项核验（部署前必须确认的两项）

本次改动引入了两个「本地跑不出来、只有线上才暴露」的风险点，已逐个核实：

**① `rel=canonical` 会不会在线上渲染成 `http://`？—— 不会。**

`base.html` 的 canonical 用 `{{ request.base_url }}` 拼接，其取值取决于 uvicorn 是否信任代理头：

| 检查项 | 实测结果 |
|--------|----------|
| `docker/supervisord.conf` 的启动命令 | `uvicorn src.main:app --host 127.0.0.1 --port 8000 --workers 1` |
| uvicorn（0.49.0）`proxy_headers` 默认值 | **True** |
| `forwarded_allow_ips` 默认 | `None` → 回落到 `127.0.0.1` |
| nginx 是否设置 `X-Forwarded-Proto` | ✅ `docker/nginx.conf:73` `proxy_set_header X-Forwarded-Proto $scheme;`（同一容器内经 `127.0.0.1:8000` 转发，来源 IP 可信） |

→ 线上 `request.base_url` = `https://codex-switch.cloud/`，canonical 与 og 域名一致。

**② 替换的截图会不会被 CDN 缓存住，用户仍看到 v1.0.6 旧图？—— 会，所以改用了新文件名。**

`docker/nginx.conf` 对 `/static/` 设了 `expires 7d` + `Cache-Control: public, immutable`，腾讯云 CDN 也在缓存该路径。实测（改动前的线上）：

```
GET /static/images/guide/step-config-switch.png          → X-Cache-Lookup: Cache Hit, Content-Length: 488755（旧图）
GET /static/images/guide/step-config-switch.png?v=20261007 → X-Cache-Lookup: Cache Hit, Content-Length: 488755（同一对象）

GET /static/css/apple.css            → ETag "6a9ec339-92c4", Expires 同下
GET /static/css/apple.css?v=1        → ETag "6a9ec339-92c4", Expires 同上
GET /static/css/apple.css?v=20260909 → ETag "6a9ec339-92c4", Expires 同上
GET /static/css/apple.css?v=zzz999   → ETag "6a9ec339-92c4", Expires 同上
```

**结论：该 CDN 对 `/static/` 忽略 query string**——`?v=` 形式的缓存刷新在这个链路上**不生效**（项目里 `base.html` 一直靠 `?v=YYYYMMDD` 给 css/js 做版本，实际穿不透 CDN；本次未改 css/js，所以没有暴露问题，但这是个既有认知偏差，已记入项目记忆）。

因此截图的替换**采用改名**：`step-config-switch.png` → **`step-config-switch-v3.png`**（新 URL = 必然 cache miss），`guide.html` 两处引用同步更新，旧文件已移除。新文件 `step-tools-status.png` 本就是新 URL，无此问题。

> 对比之下 **HTML 不受影响**：`src/main.py` 的 `no_cache_html` 中间件给所有 `text/html` 加 `no-store`，线上实测 `GET /` 为 `Cache Miss`，所以模板类改动部署后立即生效。
