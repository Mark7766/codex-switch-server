## 0. 结论速览（按修复优先级重排）

客户端在 2026-09-07 ~ 2026-09-10 之间，从 2.3.0 一路走到 **3.0.0**，完成了一次**破坏性转型**：

> **从「本地代理工具」变成「纯配置工具」**——本地转发服务被整段删除，Agnes 供应商下线，插件子系统 / 日志页 / 帮助页移除，遥测口径收窄为「只上报配置操作、零个人数据」。

服务端**没有任何一个提交跟随这次转型**。

**当前支持的三家供应商**（客户端 v3.0.0 事实，报告全文以此为准）：

| 供应商 | Codex 端点 | Claude 端点 | 模型 |
|--------|-----------|-------------|------|
| **DeepSeek** | `https://api.deepseek.com/` | `https://api.deepseek.com/anthropic` | `deepseek-flash` / `deepseek-v4-pro` |
| **智谱 GLM** | `https://open.bigmodel.cn/api/v1` | `https://open.bigmodel.cn/api/anthropic` | `glm-5.3` / `glm-5.3-flash` / `glm-5.2` |
| **自定义** | 用户自填（OpenAI Responses 兼容） | 用户自填（Anthropic 兼容） | 用户自选 |

> 三家**均为直连**（无本地代理）；Agnes 已于 v3.0.0 下线，不再支持。

## 5. P3：数据面 —— 遥测契约与指标（**原 P0，本次下调**）

> **为什么下调**：这一组问题**不影响任何用户可见流程**——客户端把 4xx 当作丢弃、不报错，用户端一切正常；受影响的只有后台数据采集与统计。按「先修用户看得见的」，放到内容之后处理。

### 5.1 遥测上报 422：`client_id` 契约断裂

**证据（客户端侧）** —— `codex-switch/electron/server-client/telemetry.ts`：

```ts
/**
 * 上报体（v3.0.0 收窄）。
 * 不要再加回 client_id —— 它是持久设备标识符，属《个人信息保护法》下的个人信息。
 */
export interface TelemetryPayload {
  app_version: string;
  platform: string;
  arch: string;
  os_version: string;
  events: TelemetryEvent[];
}
```

实际 POST 的 body 也只包含上述 5 个字段（`telemetry.ts` 的 `flush()`），**不含 `client_id`**。

**证据（服务端侧）** —— `codex-switch-server/src/schemas/telemetry.py`：

```python
class TelemetryPayload(BaseModel):
    client_id: str          # 必填（无默认值）
    app_version: str = ""
    # ...
```

以及 `src/api/v1/telemetry.py` 在写入时用 `payload.client_id` 做 `ClientRegistry` 自动注册。

**影响**：

- v3.0.0 客户端每次上报 → Pydantic 返回 **422 Unprocessable Entity**；
- 客户端把 4xx 当作「丢弃」（`telemetry.ts` 中 `res.status >= 400 && < 500` 分支不重试），因此**事件被静默丢弃**；
- `client_registry` 不再由遥测路径自动注册；
- 管理后台 / 社区统计的来源之一被切断。

> 隐蔽点：**服务端对最新客户端「完全收不到遥测」**，而两边都不报错（客户端静默、服务端只是一条 422 访问日志），所以很难被发现——但**用户无感**，这也是它不占 P0 的原因。

**建议修复方向（择一或组合）**：

| 方案 | 做法 | 代价 |
|------|------|------|
| A（推荐，最小改动） | 服务端 `client_id: str = ""` 改为可选；所有依赖处对空值做保护（自动注册跳过、`active_users` 用 `client_registry` 或新口径） | 需同步改 `telemetry.py`、`client.py`、`services/telemetry.py` 与测试 |
| B | 与服务端约定一个新的**每次会话随机、不落盘**的匿名 id | 客户端也要改，超出「仅服务端」范围 |
| C | 在 A/B 之外保留旧客户端兼容（老客户端仍带 id） | 必选，A/B 都应叠加此项 |

### 5.2 「早期成员 / 加入日期 / 活跃用户」口径失真（同一根因）

**证据** —— `src/api/v1/client.py`：

```python
# Joined date: earliest app_start
joined = await db.scalar(
    select(func.min(TelemetryEvent.created_at)).where(TelemetryEvent.client_id == client_id)
)
# Early member: first used Codex Switch before v1.11.0 shipped
v111_ship_date = datetime(2026, 6, 17)
is_early = bool(joined and joined < v111_ship_date)
```

```python
# community_stats
active = await db.scalar(
    select(func.count(func.distinct(TelemetryEvent.client_id))).where(
        TelemetryEvent.created_at >= cutoff, TelemetryEvent.client_id != ""
    )
)
```

**影响**：v3.0.0 客户端不再上报 `client_id` 与 `app_start`，于是：

- `joined_date` 对纯 3.0.0 用户恒为空，`is_early_member` 恒 false；
- `active_users`（30 天活跃）将随 90 天数据清理逐步归零；
- 侧边栏「和 X 位朋友一起使用」目前读的是 `total_clients`（`client_registry` 行数），**该口径仍可用**（客户端启动时仍会调用 `/client/{client_id}/profile` 触发注册），但 `active_users` 会变成孤儿指标。

**建议**：与 5.1 一并决策——明确「是否还需要 active_users / 早期成员」这两个依赖 `client_id` 的指标；若保留，改用 `client_registry.created_at`（加入时间）与 `/client/*/profile` 访问记录作为新数据源。

> 顺带发现（口径不一致，低优先）：服务端阈值硬编码 `2026-06-17`，客户端本地兜底用的是 `2026-06-16`（`electron/main.ts` `communityGetProfile`）。两侧应统一到同一常量。

## 11. 风险与注意事项

1. **用户可见内容优先**：门户文案是第一优先级；遥测契约虽曾是 P0，但用户无感，放在内容之后处理不会造成用户侧问题。
2. **遥测契约的改动方向会分叉**：可选 `client_id` 能让 3.0.0 上报「活过来」，但**拿不回设备级身份**（客户端是刻意去掉的，属合规考量）。因此 `active_users` 之类指标要么换数据源，要么正式下线，**不要试图让客户端把 `client_id` 加回来**。
3. **老客户端兼容**：2.x 客户端仍会发送带 `client_id` 的遥测、仍可能调用 `/plugins`。任何「删除」动作都应先用访问日志确认无存量调用，或先降级为 deprecated。
4. **文档单一来源**：`doc-codex-switch.html` 正文是一次性改写的（非运行时拉取），改完后客户端再发版仍会漂移；建议在每个文档页顶部加「内容对应客户端 vX.Y.Z」的可见标注，降低下次漂移的追踪成本。
5. **不要动下载 / 更新链路**：这是当前唯一完全健康的子系统（COS 稳定 key + GitHub 兜底 + 3.0.0 缓存已就位），改动风险高于收益。
6. **`llms.txt` 的传播面**：它被 AI 爬虫直接引用，错误定义会被二次放大；建议与门户正文**同期**修正。
