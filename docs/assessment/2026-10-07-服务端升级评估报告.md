## 0. 结论速览

### 0.1 一句话结论

客户端在 2026-09-06 ~ 2026-09-10 之间连发 **v2.1.0 → v2.2.0 → v2.3.0 → v3.0.0**，完成一次**破坏性转型**：**从「本地代理工具」变成「纯配置工具」**（本地转发服务整段删除、Agnes 供应商下线、插件/日志/帮助页移除、遥测收窄为「只上报配置操作」）。

服务端自 `67edb33`（2026-09-07）**没有任何一个提交跟随这次转型**。

**视觉验证的直接结论**：本机运行的客户端主界面已经是「设置 + 工具接入状态」两个入口、供应商只有 DeepSeek / 智谱 GLM / 自定义；而生产门户 **4 个面向用户的页面（首页 / 下载页 / 使用指南 / Codex Switch 工具文档）全部仍在讲「本地代理」「端口 11435」「Agnes」「启动代理」**（另 2 个 ai-* 工具文档页健康），连使用指南里配的界面截图都是 **v1.0.6 时代**（左下角还写着「代理 已停止」）。

### 0.2 优先级总览

排序原则：**先修用户看得见的内容**；遥测契约（不影响用户）排后。

| 优先级 | 主题 | 影响面 | 说明 |
|--------|------|--------|------|
| **P0** | 门户四页文案 + 界面截图 | 用户直接可见 | 首页 / 下载页 / 使用指南 / 工具文档页仍在承诺已删除的「本地代理」能力 |
| **P1** | `llms.txt` + `base.html` 结构化数据 + `/support` 404 | 用户 / 爬虫 / 搜索引擎可见 | 输出给 AI 与搜索引擎的产品定义是错的；页脚/悬浮入口指向 404；百度验证码是占位符 |
| **P2** | `/plugins/*`、`/update/check` 亮点、遥测事件白名单 | 内部 / API | 冗余与过时，不影响用户 |
| **P3** | 遥测契约（`client_id`）与后台指标失真 | 数据面 | v3.0.0 遥测全部 422 被静默丢弃；用户无感 |
| **P4** | 域名 / 版本号 / 记忆文件一致性 | 卫生 | 长期收尾 |

## 6. 最小化修改策略（非必要不修改）

> 本次升级的目标是「**把过时内容改对**」，不是「重构」。每一处改动都必须回答一句话：**不改它，用户会看到错的东西吗？** 答不上来就不改。

### 6.1 三条硬性纪律

1. **只改有证据的过时点**：每处修改必须能对应到 §4 清单里的一个编号（`C-xx`）或 §0.3 的一条新发现（`N-x`）。对不上编号的改动一律不做。
2. **不做顺带优化**：过程中若发现 `is_critical` 推导不严谨、注释措辞不准、代码可读性可改进等——**只记录、不修**（这些已作为观察项写在 §4 里）。
3. **改文案优先于改结构**：能用替换字符串解决的，就不动模板结构、不动 CSS、不动 JS 逻辑。

### 6.2 按「改动风险」分三档，高风险默认不做

| 档位 | 典型动作 | 处理方式 | 示例（本报告编号） |

### Phase 0 — 门户文案与截图对齐（P0，约 1–2 天）

1. **确定唯一事实来源**：以客户端 `CHANGELOG.md [3.0.0]` + `docs/help/faq.json` + `electron/config/providers.ts` 为准（三家供应商、`deepseek-flash`/`deepseek-v4-pro`、`glm-5.3` 系列）。

### Phase 1 — SEO / GEO / 支持入口（P1，约 1 天）

1. `base.html`：description / keywords / JSON-LD 去 Agnes 去「代理」（C-23、C-25、C-27）；`og:url`、`og:image` 统一新域名（C-24）；补 `rel=canonical`（C-28）；处理百度验证码占位符（C-26）。
2. `router.py`：重写 `llms.txt` 全部过时段落（C-19 ~ C-22）。
3. **`/support` 三选一**（必须收口，当前是「robots 允许 + llms 链接 + sitemap 没有 + 实际 404」的矛盾状态）：
   - 方案 A（推荐、成本最低）：**先落一个轻量 `/support` 页**（复用现有 `.doc` 布局 + 页脚/导航「支持」链接 + 已有微信二维码弹窗内容），并把 `/faq` 301 到 `/guide#faq` 或同样落页；
   - 方案 B：暂不建页，把 `robots.txt` 的 Allow 与 `llms.txt` 的链接一起撤掉；
   - 方案 C：`/support` 302 重定向到 `/guide`。

4. **验收**：`/support` 返回 200（或 301/302 到有效页）；`robots/sitemap/llms` 三处页面清单一致；`llms.txt` 的产品定义正确。

### Phase 3 — 遥测契约止血（P3，约 1 天）

1. `TelemetryPayload.client_id` 改为可选 `str = ""`（C-34）；`telemetry.py` 对空值跳过 `ClientRegistry` 注册（C-35）。

3. 统一「早期成员」阈值常量（服务端 `2026-06-17` vs 客户端 `2026-06-16`）。

3. **到此为止，仅在本地**。不执行 `git push`、不执行 `docker compose up`。

## 10. 风险与注意事项

1. **不要试图让客户端把 `client_id` 加回来**。客户端是**刻意**移除的（文档里明确写属《个人信息保护法》下的个人信息）。正确解法是服务端容忍缺省，而不是回退客户端。
2. **老客户端兼容**。2.x 客户端仍会带 `client_id`、仍可能调 `/plugins`。所有删除动作都要先看访问日志或降级为 deprecated。
3. **文档单一来源会持续漂移**。`doc-codex-switch.html` 是一次性改写，客户端再发版就会再次漂移；建议每页标注「内容对应客户端 vX.Y.Z」，并把「客户端发版 → 检查门户」写进发版清单。
4. **截图比文字更容易被忽略**。本次评估发现的 v1.0.6 截图说明「改文字不改图」会留下最刺眼的破绽，建议把「门户截图与客户端版本一致」列入 Phase 0 验收。
5. **不要动下载 / 更新链路**。这是当前唯一完全健康的子系统（COS 稳定 key + GitHub 兜底 + `data/codex-switch/3.0.0/` 已就位），改动风险高于收益。
6. **`llms.txt` 传播面最广**。它被 AI 抓取器直接引用，错误定义会被二次放大，建议与门户正文同期修正。
7. **待你确认的一项事实**：客户端 CHANGELOG 3.0.0 写着「V4 Pro 将在北京时间 2026-09-14 12:00 之后由 Flash 接管」，截至本次评估（2026-10-07）该时点**已过**；但客户端与本机实测界面里 `deepseek-v4-pro` 仍作为 Opus 档默认值存在。建议向 DeepSeek 官方确认 `deepseek-v4-pro` 是否仍在服务，再决定门户文案里是否保留该模型名。
8. **最小化修改纪律**（详见 §6）：本次以「改对内容」为目标，**任何重构、优化、依赖升级一律不做**。高风险档（改 schema、改公共代码路径、删端点）**默认不做**；确需做时必须先单独确认。
9. **验收必须是全量，不能只测改动点**：「改 A 坏 B」在本项目有两处高发区——`base.html`（改动会影响全站 6 个页面的 OG / JSON-LD）与 `schemas/telemetry.py`（改动会影响所有写入路径与后台图表）。§8 的第 2~5 层就是专门为这类连带影响设计的。
10. **不自动 push / 部署**（详见 §9）：这是本次的硬性要求，任何「先推上去再说」「先部署看看」的做法都不允许。
11. **验收环境不要用生产凭据**：本地 `.env` 用独立测试 token 与独立数据库，避免验收过程污染生产数据或被生产数据误导。
